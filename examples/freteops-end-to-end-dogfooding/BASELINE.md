# FreteOps Dogfooding Baseline

## Date

2026-10-15

## Baseline type

Near-greenfield adoption.

AISDD was introduced during the first development session, immediately after the first Android scaffold and prototype behavior were generated.

This is not a Recovery Mode case.

## Starting project condition

Before AISDD was introduced, the project already had a generated Android prototype with working local interactions and mock data.

Source review confirmed the following facts:

### FACTS

- The application is a native Android project.
- The implementation language is Kotlin.
- Jetpack Compose is used for UI.
- UI state is managed through a ViewModel and StateFlow.
- A repository interface separates UI/state logic from the shipment data source.
- A mock repository provides prototype shipment results.
- Search accepts a transport-document or invoice-like identifier.
- Detail presentation already includes shipment status, parties, route, schedule-like fields, occurrences, and history.
- No real transport-system backend integration exists at this baseline.
- No production authentication flow exists at this baseline.
- The generated theme follows system light/dark mode.
- Several UI elements use fixed color constants instead of semantic theme colors, creating contrast problems in dark mode.
- The Android package/application identifiers are still prototype identifiers generated by the AI Studio environment.

### ASSUMPTIONS

- The repository abstraction will remain the initial boundary for replacing mock data with a real API implementation.
- The product will evolve incrementally rather than by rewriting the generated project.
- Authentication and external integration will be added only after the basic project structure and UX are stable enough to support them safely.

### UNKNOWNS

- Final application name and package identifier.
- Final backend hosting and API topology.
- Final authentication contract.
- Exact external-system integration contract exposed to the Android client.
- Persistence strategy for recent searches and local state.
- Release signing and long-term key custody process.

### RISKS

- Generated mock behavior may be mistaken for real integration if project state is not documented clearly.
- Large AI-generated Compose files may become difficult to maintain if incremental boundaries are not enforced.
- AI tools may introduce Firebase, authentication, navigation, storage, or architectural dependencies without a real requirement.
- Repeated manual prompts could become the real source of truth unless repository docs are kept current.
- Product-specific integration knowledge could leak into UI or mobile code if API boundaries are not preserved.

## Human goal

Build FreteOps as a practical logistics operations app that begins with simple shipment lookup and can later grow into broader operational workflows without being tied to a single company or operating unit.

## Tooling model at baseline

| Tool | Role |
|---|---|
| Gemini / Google AI Studio | Android implementation and live UI preview |
| GitHub | Versioned project source and AISDD memory |
| ChatGPT | Architecture/specification review and AISDD governance |
| Human owner | Product truth, priorities, testing, approval |

No other Google service is considered mandatory at baseline.

Services such as Firebase may be introduced later only if a concrete requirement justifies them.

## Prompt baseline

The initial Android prototype was generated from a long manually written request containing product context, stack, architecture guidance, UI requirements, and exclusions.

Classification:

```txt
PML-0
```

Reason:

The prompt itself carried most of the project context.

## AISDD adoption state

The project is moving directly into repository-driven development with these goals:

- one task per cycle;
- explicit product and architecture memory;
- acceptance checks before moving forward;
- short handoff after each meaningful cycle;
- progressive PML reduction;
- cross-AI continuation between ChatGPT and Gemini.

## First controlled task

```txt
UX-001
```

Goal:

Improve legibility, contrast, and visual hierarchy of the existing screens without changing functional behavior, repository contracts, mock behavior, domain models, or external integration behavior.

This task was chosen because it is low-risk and easy to validate visually while testing the AISDD execution loop.

## Baseline success criteria for the dogfooding case

The case will be considered useful if, over multiple real cycles:

- prompts become materially shorter;
- Gemini can execute repository-defined tasks without repeated manual recaps;
- handoffs remain accurate enough for ChatGPT or another AI to continue;
- architecture and business boundaries survive incremental changes;
- known unknowns remain explicit instead of being silently invented;
- documentation does not become a maintenance burden larger than the value it provides;
- the project reaches a real Android distribution milestone while preserving traceable decisions.
