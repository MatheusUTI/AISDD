# FreteOps End-to-End Dogfooding Case

FreteOps is the first AISDD dogfooding case intentionally tracked from the project's first development day through a real Android release lifecycle.

It complements the existing Recovery-focused cases. The project did not begin as a mature or messy codebase: AISDD was adopted immediately after the initial generated Android scaffold, while architecture, product boundaries, and implementation behavior were still easy to shape.

## Purpose

Use FreteOps to test whether AISDD can keep a new AI-assisted product coherent while:

- product requirements evolve incrementally;
- two different AI systems collaborate on the same project;
- implementation is generated by an AI coding environment;
- architectural decisions remain human-governed;
- prompts intentionally become shorter over time;
- repository documentation becomes the primary project memory;
- a prototype grows into an installable and distributable Android application.

The central question is:

> Can AISDD reduce manual context while keeping a real project safe, understandable, and portable across AI tools from early prototype to release?

## Project summary

FreteOps is an Android logistics operations application.

Its initial scope is intentionally small:

- search by transport document or invoice identifier;
- show shipment and delivery information;
- evolve later toward operational functions such as scheduling, collections, vehicles, occurrences, routes, proof of delivery, and alerts.

The project is designed to remain independent from one company or one operational unit.

## AI collaboration model

The dogfooding intentionally separates responsibilities:

| Role | Current tool/person | Responsibility |
|---|---|---|
| Product owner / validator | Human | Product decisions, operational truth, acceptance |
| Specification / architecture / review | ChatGPT | Project framing, AISDD governance, code/repository review |
| Android implementation | Gemini in Google AI Studio | Execute one repository-defined task at a time |
| Source of truth | Git repository | Specs, rules, state, decisions, next task, handoff |

The goal is not to prove one AI tool is better than another.

The goal is to test AISDD portability between them.

## Why this case matters

FreteOps validates a different path from the existing Recovery cases:

```txt
Idea
↓
Initial AI-generated scaffold
↓
Immediate AISDD adoption
↓
One-task execution cycles
↓
Cross-AI review and handoff
↓
Real integrations
↓
Internal Android release
↓
Continued product evolution
```

This makes it useful for testing:

- greenfield and near-greenfield adoption;
- AI-generated Android architecture;
- prompt shrinkage from PML-0 toward PML-4;
- repository-first continuity;
- cross-AI execution;
- design and refactor guardrails;
- contract preservation during integration work;
- long-running project memory.

## Current project state at dogfooding start

AISDD was adopted during the first development session, after the initial Android prototype was generated.

The initial source review confirmed:

- native Android project;
- Kotlin;
- Jetpack Compose;
- ViewModel-based state management;
- repository abstraction between UI and data source;
- mock shipment data for prototype behavior;
- no real external transport-system integration yet;
- UI contrast and theme problems identified as the first isolated task.

The first AISDD-controlled implementation task is intentionally cosmetic and low-risk so the workflow can be validated before real integrations are introduced.

## Project-side AISDD target structure

The FreteOps repository should maintain:

```txt
docs/
├─ START_HERE.md
├─ 00_PROJECT_RULES.md
├─ 01_PRODUCT_SPEC.md
├─ 02_ARCHITECTURE.md
├─ 03_CURRENT_STATE.md
├─ 04_NEXT_TASK.md
├─ 05_ACCEPTANCE_CHECKS.md
├─ 06_DECISIONS_LOG.md
├─ 07_HANDOFF.md
├─ 08_KNOWN_ISSUES.md
└─ 09_FILE_INDEX.md
```

Additional test and engineering documents should be introduced only when real project pressure justifies them.

## Prompt maturity experiment

The first implementation request was a long manually supplied prompt and is classified as PML-0.

After AISDD adoption, the intended progression is:

```txt
PML-0 → PML-2 → PML-3 → PML-4
```

Target prompt:

```txt
Read docs/START_HERE.md.
Execute docs/04_NEXT_TASK.md.
```

If that prompt fails because project context is missing, the preferred response is to improve repository memory rather than expand the chat prompt.

## Dogfooding rules

For FreteOps:

1. Gemini implements changes in the FreteOps repository.
2. ChatGPT reviews architecture, project memory, and AISDD evidence.
3. Product behavior is accepted by the human owner.
4. One implementation task is executed per cycle.
5. Important decisions must leave chat and enter the repository.
6. `07_HANDOFF.md` must be refreshed at meaningful cycle boundaries.
7. Shorter prompts are tested deliberately rather than assumed to work.
8. Core AISDD rules are not changed from one isolated success or frustration.
9. Failed experiments are evidence and must be recorded.
10. Public AISDD dogfooding notes must not expose credentials, private operational data, or proprietary integration details.

## Lifecycle checkpoints

Track evidence at these milestones:

- initial generated prototype;
- AISDD adoption baseline;
- first successful repository-driven task;
- first successful PML-3 task;
- first successful PML-4 task;
- first real backend/API integration;
- first authentication implementation;
- first cross-AI continuation without manual recap;
- first device-installed build;
- first internal distribution build;
- first post-release feature cycle.

## Evidence files

- `BASELINE.md` — factual starting point.
- `CYCLE_LOG.md` — chronological execution history.
- `METRICS.md` — dogfooding metrics and PML tracking.
- `LESSONS.md` — observations and candidate framework changes that are not yet promoted to AISDD core rules.
